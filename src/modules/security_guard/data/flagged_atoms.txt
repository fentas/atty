# Atomic threat fragments — V2-G AtomMatcher data file.
#
# Single source of truth. Both atty-guard (Rust, `include_str!` →
# `aho-corasick`) and atty's in-proc security_guard (Zig,
# `@embedFile` → linear scan; AC is over-engineered for in-proc
# until atty grows beyond a couple hundred patterns) read THIS
# file. One atom per line; `#` comments and blank lines stripped
# at parse time.
#
# Atom design rules (read before adding entries):
#   - Min length 3 characters — anything shorter is high-FP noise.
#   - Prefer COMMAND FRAGMENTS over WORDS — `nc -e` beats `nc`.
#   - Prefer SYMBOL-DENSE strings — `/bin/sh -i` beats `bin/sh`.
#   - The matcher is case-sensitive substring; don't try to encode
#     case-insensitivity here, write both forms instead.
#   - One incident per section. Cite source in the comment.
#
# Verdict mapping (today, until the threat-level accumulator
# lands as V2-J):
#   - Any single atom hit → Verdict::Warn at confidence 0.6.
#   - The OnnxBackend's sliding-context-window (V2-H) will use
#     the atom match position to slice the SLM input — turning
#     a low-confidence broad signal into a high-confidence
#     verdict via deeper context.
#
# Adding a new atom: PR with the entry + a regression test in
# `atom_matcher.rs` tests asserting the new atom hits.
# Removing: same — drop the entry + remove its test.
