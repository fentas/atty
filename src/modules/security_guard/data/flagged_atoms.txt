# Atomic threat fragments — V2-G AtomMatcher data file.
#
# Today: atty-guard (Rust) reads this via `include_str!` →
# `aho-corasick`. atty's in-proc security_guard (Zig) does NOT
# load this file yet — it ships its own narrower atom set inline.
# V2-J queues a Zig-side `@embedFile` reader sharing this corpus
# once the in-proc set grows past linear-scan range. The file
# lives under `src/modules/security_guard/data/` because Zig's
# `@embedFile` only reaches files inside its package root and we
# want the eventual shared layout in place from day one.
#
# One atom per line; `#` comments and blank lines stripped at
# parse time.
#
# Atom design rules (read before adding entries):
#   - Min length 3 characters — anything shorter is high-FP noise.
#   - Prefer COMMAND FRAGMENTS over WORDS — `nc -e` beats `nc`.
#   - Prefer SYMBOL-DENSE strings — `/bin/sh -i` beats `bin/sh`.
#   - The matcher is case-sensitive substring; don't try to encode
#     case-insensitivity here, write both forms instead.
#   - One incident per section. Cite source in the comment.
#
# Verdict mapping (today, until the threat-level accumulator
# lands as V2-J):
#   - Any single atom hit → Verdict::Warn at confidence 0.6.
#   - The OnnxBackend's sliding-context-window (V2-H) will use
#     the atom match position to slice the SLM input — turning
#     a low-confidence broad signal into a high-confidence
#     verdict via deeper context.
#
# Adding a new atom: PR with the entry + a regression test in
# `atom_matcher.rs` tests asserting the new atom hits.
# Removing: same — drop the entry + remove its test.

# ---------------------------------------------------------------
# CVE-2026-31431 / copy.fail. AF_ALG socket creation at the kernel
# layer is the V2-G eBPF tracepoint's job (PR #117) — that's the
# primary detector. These atoms are a backstop for the rare case
# where the user runs a published PoC ONE-LINER at the shell that
# names the AF_ALG family / algif_aead module directly. Most legit
# AF_ALG use is library-internal (dmcrypt, fscrypt, libgcrypt) —
# rarely typed verbatim at a shell. `splice(` is NOT included even
# though splice() is one half of the exploit — splice() has too
# many legitimate uses (zero-copy file/socket I/O) to flag on its
# own. The kernel-side eBPF tracepoint correlates AF_ALG + splice
# at the syscall layer where the FP rate is near zero.

socket.AF_ALG
af_alg_set
algif_aead

# ---------------------------------------------------------------
# Shai-Hulud dead-man switch + credential harvest. The Sep-2025 →
# May-2026 wave installs a systemd-user daemon that polls GitHub
# every 60s; if it sees the stolen tokens get revoked it fires
# `rm -rf ~/` to scorch the user's home. We catch the destruction
# command shape — the most damaging step — verbatim, so a banner
# fires before bash splits the line. `/proc/self/mem` catches the
# self-scrape variant of the credential-extraction step. The
# `/proc/<pid>/mem` cross-process variant is intentionally NOT an
# atom — Aho-Corasick treats `*` as a literal character, so a
# glob-shaped pattern wouldn't match `/proc/1234/mem` anyway, and
# enumerating every plausible PID would bloat the automaton. eBPF
# (V2-G) tracks `openat()` on `/proc/<pid>/mem` at the kernel
# layer, which is the correct detection point for that variant.

rm -rf ~/
rm -rf $HOME
rm -rf ${HOME}
rm -rf /home/
rm -rf "$HOME"
/.aws/credentials
/.npmrc
/.ssh/id_rsa
/.ssh/id_ed25519
/.ssh/id_ecdsa
/proc/self/mem

systemctl --user enable
